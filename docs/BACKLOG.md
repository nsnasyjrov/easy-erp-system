## 4 Автотесты для CHANGE EMAIL ENDPOINT

##  1. Смена email содержит реальный дефект очереди

Статус: на тестировании.

`UserEmailChangeConveyNotification` выполняется через очередь и читает актуальный объект `User`.

Если пользователь подтвердит новый email раньше обработки очереди:

- предупреждение может уйти уже на новый адрес вместо старого;
- `pending_email` внутри письма окажется `null` либо новым значением.

Нужно заранее сохранить `$oldEmail` и `$pendingEmail` и отправлять через `Notification::route('mail', $oldEmail)`.

Дополнительно текущий `pending_email`:

- остаётся в БД после истечения 60-минутной ссылки;
- из-за `unique` может бессрочно резервировать адрес;
- повтор того же значения отправляет ещё одну ссылку;
- замена значения инвалидирует старую ссылку — это как раз разумное поведение;
- в `ChangeEmailUserRequest` остался мёртвый `withValidator()` для уже удалённого `current_email`.



## 3 Тестовое окружение не соответствует production

	Статус: На тестировании

Основной СУБД проекта является PostgreSQL, при этом PHPUnit сейчас использует SQLite in-memory.

Код уже содержит PostgreSQL-специфичные конструкции, например `ILIKE`. Поэтому успешное выполнение текущих тестов не гарантирует работоспособность поиска, фильтров, ограничений и миграций в production. При появлении Feature-тестов поиска часть запросов либо упадёт на SQLite, либо PostgreSQL-специфичное поведение останется непроверенным.

Позже необходимо:

- создать отдельную PostgreSQL-базу для тестов;
- перевести PHPUnit с SQLite на PostgreSQL;
- использовать ту же основную версию PostgreSQL, что и в production;
- добавить PostgreSQL service container в GitHub Actions;
- проверять `migrate:fresh`, rollback и Feature-тесты на PostgreSQL.

До этого зелёные тесты следует воспринимать как проверку бизнес-кода и базовых HTTP-сценариев, но не как подтверждение совместимости с production-БД.
